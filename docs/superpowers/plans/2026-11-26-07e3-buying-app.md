# Part 7e-3: Buying Screens in the App Implementation Plan

**Goal:** the owner-approved design (`docs/superpowers/specs/2026-11-26-07e3-buying-app-design.md`, approved 2026-11-26): checkout and payment, orders and tracking, received and cancel, disputes, reviews, the notices inbox and push.

**Architecture:** `app/lib/features/buy/`. Hand-parsed models, three repositories behind interfaces (`CheckoutRepository`, `BuyOrdersRepository`, `InboxRepository`) with Dio implementations and fakes. The payment view is behind a provider so tests can replace the platform webview; its decisions (is this the return page, may it navigate here) are pure functions. Push sits behind a `PushService` interface with a real FCM implementation that starts only when the buyer agrees, and fails quietly without Firebase files. Photo capture, preparation and upload are 7e-2's. The server gains one field: `GET /app/config` also answers `payment_return_url` (the configured `PUBLIC_REDIRECT_URL`), so the webview knows when to close.

## Global constraints

- The app never decides a payment succeeded: only `GET /checkout/{id}` does.
- Addresses, handover codes, payment URLs and push tokens are held in memory only and never logged, put in routes or in notification text. Models holding them have a redacted `toString`.
- One idempotency key per checkout attempt, made when the review screen opens and reused on retry.
- `Tokens` spacing, `context.tokens` colours, press feedback on every control. Copy in `BuyStrings`.
- Checks from `app/`: `build_runner`, `dart format --output=none --set-exit-if-changed .`, `flutter analyze`, `flutter test`. Never claimed run on a device. No AI attribution in commits.

## Tasks

1. Server: `payment_return_url` in `/app/config` (test). App: `AppConfig.paymentReturnUrl`.
2. Models and repositories, fakes, strings.
3. Checkout: address, options per group, review, pay with idempotency, `allocation_changed` refresh.
4. Payment view and the polling result (pure redirect and navigation rules).
5. Orders list and detail, tracking with the handover code and pickup point, received, cancel.
6. Report a problem (photos), dispute status, withdraw; review.
7. Inbox, unread count, tap routing; `PushService`, permission at first paid order, register and remove.
8. Cart and Account entry points; wire check; README, roadmap and plan status; full checks.
