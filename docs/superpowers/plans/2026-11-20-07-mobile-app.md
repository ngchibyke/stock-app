# Part 7: Mobile App (Flutter), Overview and Sub-plans

> **For agentic workers:** this is the overview. The task-by-task plans are the sub-plans listed below; only **7a** is written. Each later sub-plan is written once the one before it lands, so it builds on real interfaces (the convention in the roadmap).

**Goal:** One Flutter app, for Android and iPhone, where a buyer browses Abuja's stores, pays into escrow, tracks the order and confirms delivery, and where a seller who redeemed an access code runs up to two stores. It is the product the owner's dashboard supports: the screens the spec calls "polished, not templated" (tracking and checkout) live here.

**Spec:** `docs/superpowers/specs/2026-10-22-abuja-marketplace-design.md`, mainly §1 (anti-goals), §2 to §4 (roles, stores, products), §5 to §6 (payments, delivery, the tracking screen), §7 to §10 (chat, disputes, reviews, notifications) and §13 (data protection). Also read the "Carried forward" and go-live lists in `docs/superpowers/plans/2026-10-23-00-roadmap.md`.

## What the server is missing for an app

Found by reading the routes against the spec. These block the app, so they come first, as sub-plan 7a.

| Gap | Why it blocks |
|---|---|
| **No browsing or search.** Products are only listed per store and shown one at a time. There is no catalog, no store directory, no category list. Product `category` is free text. | A buyer cannot discover anything. The spec leaves "search and category structure" to the builder. |
| **No photo upload.** Products, stores, reviews and disputes carry `photo_keys`, but nothing lets a phone put a photo anywhere, and nothing turns a key into something an app can display. | No product can be listed with a photo; no review or dispute can carry evidence. The roadmap already requires that a key belong to the uploader. |
| **No account recovery.** There is no way back into an account after a forgotten password. | A phone app that cannot recover an account loses users and floods support. |
| **OTP goes to the log.** `LogOtpSender` is the only sender; no SMS provider exists. A throttled resend can return a `verification_id` whose code was never sent. | Nobody can sign up on a real phone. |
| **No courier location.** `GET /orders/{id}/tracking` returns steps, contact and a `tracking_url`, but no coordinates. | Spec §6 item 5 (a map while out for delivery) cannot be built. The app links to the courier's tracking page instead; see decision D9. |

## Architecture decisions

*(my call)* each is a default; change it before 7b starts if you disagree.

- **Flutter, one codebase, `app/` at the repo root.** Android and iOS. No web build.
- **State: Riverpod** (`flutter_riverpod`). Providers per feature, repositories behind interfaces so tests swap in fakes.
- **Navigation: `go_router`**, with a redirect that sends a signed-out user to sign-in and handles notification deep links.
- **HTTP: `dio`**, one client with an interceptor that adds the bearer header, maps the error envelope to a typed `ApiError`, and signs the user out on a 401 for an authenticated call (the same rule as the dashboard's `api.ts`).
- **Models: plain immutable Dart classes with `json_serializable`.** No `freezed`; fewer generated files to review.
- **Session: `flutter_secure_storage`** (Keychain and Keystore). The token is never written to plain preferences, logs or crash reports.
- **Money: integer kobo everywhere**, formatted only at the edge with `intl` (`en_NG`, ₦). Never a `double`.
- **Payment: `webview_flutter`** loads the `payment_url` from `POST /checkout`; the app intercepts the redirect to `PUBLIC_REDIRECT_URL`, closes the view, and polls `GET /checkout/{id}` (which already re-verifies a pending payment). The app never decides a payment succeeded.
- **Push: `firebase_messaging`.** The server already sends fixed copy plus `kind` and `notification_id`; the app maps `kind` to a screen and fetches details from the inbox.
- **Chat: `web_socket_channel`** with the bearer header (mobile only), falling back to polling from the last sequence number, as the server's design intends.
- **Photos: `image_picker`**, then the app resizes and re-encodes to JPEG before upload (`flutter_image_compress`), which also drops GPS and other EXIF data on the phone. The server does it again (7a), because a client is never trusted.
- **Images on screen: `cached_network_image`.**
- **Tests:**
  - unit tests for models, money and state;
  - widget tests for every screen state (loading, empty, error, data), with the same four states the dashboard's kit page shows;
  - golden tests for the tracking screen and the order card;
  - `integration_test` flows against a real server, the way the dashboard's Playwright tests do, run by a separate workflow (an emulator is slow, so not on every push).
- **CI:** a new `app` job runs `flutter analyze` and `flutter test` on every pull request, next to the server and dashboard jobs.
- **Design:** the visual language is chosen at the start of 7b (decision D1), with a short brainstorm and a review of the tracking and checkout screens before the rest is built. The dashboard's tokens (spacing, motion, status colours) are a starting point for a shared language, not a requirement.
- **Language:** English at launch, every string in one place so a Hausa or Pidgin version is possible later. Chat itself already handles mixed languages.

## Global constraints for every sub-plan

- Personal data (phone, address, chat text, statements, tokens, push tokens) is never logged, never put in a URL, never sent to analytics or crash reports, and never kept in plain storage. If a crash reporter is added it gets no user identifiers and a scrubber for request bodies (decision D8).
- The handover code screen blocks screenshots and screen recording (`FLAG_SECURE` on Android; a blank snapshot in the app switcher on iOS).
- The app only ever sends what the server asks for. It sends the chosen delivery option's id, never a price, and never a total. Every amount on screen comes from a server field.
- Nothing nudges a buyer to pay outside the app: no field for a phone number or bank detail in chat or product text (the server already blocks it; the app shows the server's reason and does not try to be clever).
- Every list handles four states: loading (a skeleton shaped like the list, as in the dashboard), empty (with a way forward), error (with retry) and data. A screen with a missing state is not finished.
- Accessibility: every control has a label, tap targets are at least 48 dp, text scales to 200% without clipping, colour is never the only signal, and motion respects the system's reduced-motion setting.
- Offline: the app opens and shows what it last had (read-only), says plainly that it is offline, and never queues a payment or a money action for later.
- Commits are conventional messages with no AI attribution of any kind.

## Risks

- **iOS builds need macOS.** Without a Mac, iPhone builds run in CI on a macOS runner. That is slower and costs minutes; 7g budgets for it.
- **A first store review can reject an app.** Apple and Google ask for a demo account, a privacy policy URL, and accurate data-safety answers (the app collects phone numbers, addresses, photos and chat). The go-live handbook lists these.
- **Photo handling is the riskiest server work** (untrusted images, decompression, privacy). It is isolated in 7a with its own tests and a review focus.
- **Nothing here can be tested on a real device from this machine today.** There is no Flutter or Android toolchain installed. 7b starts by installing them and writing a one-screen app that signs in against a local server, so every later task has a working loop.
