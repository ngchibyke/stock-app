# Part 7: Flutter App (buyer and seller) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The phone app buyers and sellers use (spec §12: Flutter, Android and iPhone, Abuja only). Buyers browse, chat, buy, track and confirm delivery, complain and review. Sellers open a store, list products, pack and hand over orders, answer complaints and reply to reviews. The tracking screen is the one the spec says must be "polished, not templated" (§6).

**Decision (my call): ordinary Flutter code in `app/`, not FlutterFlow.** No FlutterFlow connector or token was available, and the app is mostly typed API calls, state and animation, which suit code in the repo, under the same tests and CI as everything else. If a FlutterFlow project is wanted later, `app/openapi.yaml` (Task S4) can be imported as an API group.

**Architecture:** Feature-first folders (`lib/features/<feature>/`), one `ApiClient` (dio) that is the only thing that talks HTTP, Riverpod for state, go_router for navigation with role-aware redirects, and a small design system in `lib/ui/` (theme, motion tokens, interactive icon and button set) that every screen uses, so the feel is set in one place. Money is always integer kobo, formatted by one function. The server owns all rules; the app never recomputes prices, fees or deadlines.

**Tech stack:** Flutter (stable), Dart 3, `flutter_riverpod`, `go_router`, `dio`, `flutter_secure_storage` (session token), `web_socket_channel` (chat), `firebase_messaging` + `flutter_local_notifications` (push), `webview_flutter` (the payment provider's hosted page), `image_picker` + `cached_network_image` (photos), `flutter_animate` (motion). Tests: `flutter_test` (unit and widget), golden tests for the tracking screen, `integration_test` against a running server.

**Spec:** `docs/superpowers/specs/2026-10-22-abuja-marketplace-design.md` §3 (accounts), §4 (stores and products), §5 (payments), §6 (delivery and the tracking screen), §7 (chat), §8 (disputes), §9 (reviews), §10 (notifications), §12 and §14. Read the "Carried forward" sections of the roadmap too.

## Global constraints

- Everything in the plan 5 and plan 6 global constraints still holds for server work (`AppError` envelope, `AppJson`, `parse_id`, audit rows, no personal data in logs).
- App: no personal data in logs or crash reports; the session token only in secure storage; the app never logs a request body.
- App: every screen has loading, empty and error states (error text is the server's own message), works offline for what was already loaded, and respects the system "reduce motion" setting.
- App: every tappable thing is at least 48 dp, labelled for screen readers, and has a visible pressed state.
- **Interactive by default** (the owner's brief): every icon, button, card and list item answers touch with motion (press, hover on web builds, selection, loading, success). Motion tokens live in `lib/ui/motion.dart`: snappy springs, short travel, nothing over 400 ms except the hero moments (tracking screen, order placed).
- Abuja only: a buyer or address outside the FCT can browse but not check out ("Coming to your city soon"); the server enforces it and the app explains it.
- No shortcuts that move money from the app: the app only calls the server's routes, and shows the exact amounts the server returns.

## Server prerequisites

### Task S1: Feed, search and categories *(built: 11 tests)*

**Files:** `server/src/products/feed.rs`, `server/migrations/0039_product_search.sql`, `server/tests/feed.rs`.

- `GET /products?q=&category=&condition=&min_price_kobo=&max_price_kobo=&sort=&before=&limit=` (*built public, no sign-in, like the product page, so a visitor can browse; checkout still needs an account*). Only published products of active stores; newest first by default (`sort=price_asc|price_desc|newest`), keyset paging on `(created_at, id)`. `q` matches product name and brand with a trigram index (`pg_trgm`), case-insensitive, prefix and substring.
- `GET /categories` returns the category list. *(my call)* a fixed list owned by the server (`categories` table seeded by migration 0039). *(Built: products keep their free-text `category` so nothing already stored breaks; the feed matches a category's slug or the product's own category ignoring case, and the app's seller screens will offer this list. Enforcing the list on create is deferred to slice E.)*
- Each item carries what a card needs: id, name, price, cover photo key, store id and name, rating average and count, in-stock flag. No seller personal data.
- [ ] **Step 1:** Failing tests: only published products of active stores appear; a suspended store's products never do; `q` finds by name and brand; filters and sorts; keyset paging without overlap; a bad cursor is 422; out-of-stock items are flagged, not hidden.
- [ ] **Steps 2–5:** implement, run, `cargo clippy`, commit `feat: product feed, search and categories`.

### Task S2: Photo upload *(built: 14 tests)*

**Files:** `server/src/uploads/`, `server/migrations/0040_uploads.sql`, `server/tests/uploads.rs`.

- `POST /uploads` (signed in) takes one image and returns `{ key, content_type, bytes, width, height }`. *(Built as the raw image body with an `image/*` content type, not multipart; the type is taken from the bytes. Photos are turned upright by their EXIF orientation before the metadata is dropped; 60 uploads an hour per person; a body over 5 MB is 413; over 4096 px a side is 422 `image_too_large`.)* *(my call)* the server receives the bytes (JPEG, PNG or WebP, at most 5 MB, at most 4096 px a side), checks the magic bytes rather than the filename, strips metadata (EXIF location), re-encodes, and writes to the object store behind an `ObjectStore` trait (`S3Store` for production, `MemoryStore` for tests), following the `ToneChecker` pattern. A row in `uploads(key, uploader_id, ...)` records who uploaded it.
- **Key ownership (roadmap carry-forward):** every place that accepts photo keys must refuse a key the caller did not upload (422 `photo_not_yours`). *(Built for products (create, and update for newly added keys only, so photos from before uploads were tracked stay valid), reviews, and dispute statements and answers. Stores have no logo or banner setter yet; when one is added it must use `uploads::service::require_owned`. In a dispute the order lookup comes first, so a stranger still gets 404.)* Reuse by the same user is fine.
- `GET /photos/{key}` is not needed: photos are served from the store's public URL, built from the key by the app (`PHOTO_BASE_URL`, exposed by `/config` in Task S3). The object store is `S3Store` (an S3-compatible PUT signed with Signature V4) in production and `MemoryStore` in tests; production refuses to start without `S3_*` and `PHOTO_BASE_URL`.
- Not done here, still open from the roadmap: photos are not scanned for phone numbers.
- [ ] **Step 1:** Failing tests: wrong type, oversize and a renamed `.png` that is not an image are refused; metadata is gone from the stored bytes; someone else's key is refused on a product, a review and a dispute; the owner's own key works.
- [ ] **Steps 2–5:** implement, commit `feat: photo upload with key ownership`.

### Task S3: Push taps and app config

**Files:** `server/src/notify/` (deep link field), `server/src/config_route.rs`, tests.

- Inbox notices and pushes already carry a kind and two ids. Add a documented `route` string per kind (`order:<id>`, `chat:<id>`, `dispute:<id>`) so a tap opens the right screen. No order data, name or amount goes in a push (spec §10).
- `GET /config` (no sign-in): `photo_base_url`, `min_app_version`, `fct_only: true`, and the payment return URL scheme. A `min_app_version` the app is below shows a blocking "please update" screen.
- [ ] Failing tests, implementation, commit `feat: push deep links and app config`.

### Task S4: OpenAPI description

**Files:** `app/openapi.yaml`, `server/tests/openapi.rs`.

- A hand-written OpenAPI 3.1 description of every route the app uses, with the error envelope. A test lists the router's routes and fails if a route the app uses is missing from the file, so it cannot rot.
- [ ] Failing test, file, commit `docs: describe the app API in OpenAPI`.

### Task A2: API client and session

**Files:** `app/lib/core/api/` (`api_client.dart`, `api_error.dart`, `session.dart`), tests.

- `ApiClient` wraps dio: bearer token from secure storage, JSON in and out, the server's error envelope becomes an `ApiError(status, code, message)`, a 401 on an authenticated call signs the user out, network failures become one plain error, a per-request timeout, no body logging.
- `Money` helper: `formatKobo` (the same rule as the dashboard), kobo in and out only.
- [ ] **Step 1:** Unit tests with a fake HTTP adapter: envelope parsing, 401 sign-out (not for sign-in), token header, network error text, `formatKobo` cases.

### Task A3: Sign-up, OTP and sign-in

**Files:** `app/lib/features/auth/`, tests.

Wrong code and wrong password shake the field and say so plainly. After sign-up the app calls `verify-phone`, stores the token, loads `/me`.
- Phone entry formats as the person types and accepts `0803…`, `+234…`. The server is the judge; the app only helps.
- [ ] **Step 1:** Widget tests with a fake `ApiClient`: the whole sign-up path, a wrong code, a throttled resend, sign-in failure, token stored and cleared.

## Not in this plan

- Cities outside Abuja, cash on delivery, ads, more than two stores per user (spec §14).
- A web storefront for buyers (spec §14).
- Scanning photos for phone numbers (roadmap, owner decision).
- Notification preferences per kind (roadmap, owner decision).
- Store review of the courier map: shown only if the courier provides a location, which Shipbubble has not yet been shown to do.

## Go-live items this plan adds

- Apple and Google developer accounts, bundle ids, signing keys kept outside the repository, and store listings with the privacy labels the DPO signs off.
- The Firebase project for push (`google-services.json` and `GoogleService-Info.plist`, kept outside the repository) and APNs keys.
- Object storage and a public photo URL (`PHOTO_BASE_URL`), with a lifecycle rule for orphaned uploads.
- A privacy notice inside the app that names the processors (payment provider, courier, Anthropic for chat checks, Google for push).
